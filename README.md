## How it works

The page is rendered on the server by [site-api](https://git.belomaxorka.dev/belomaxorka/site-api)
(Go, `html/template`) with live data: now playing from Koito, service checks from Gatus, the UPS from NUT, the
home server from Proxmox, neighbours in the [otoring](https://webring.otomir23.me) webring. Everything a visitor needs
works with JavaScript off. On top of that, [htmx](https://htmx.org) refreshes the live units and
[Alpine.js](https://alpinejs.dev) handles the small interface state. No build step (Node only for the tools in `docs/tools`).

- `templates/`: `layout.html` and `index.html`, one component per rack unit in `templates/units/`, the light version
  (HTML 4.01 for old browsers, `lite.belomaxorka.dev`) in `templates/lite/`
- `content/*.yaml`: what the page lists (racks, contacts, buttons, donations, lamps, the profile, the hardware's names,
  the addresses the templates link to in `links.yaml`); edit and push, no code
- `templates/infra.html`: [infra.belomaxorka.dev](https://infra.belomaxorka.dev), where «hosted on belomaxorka
  infrastructure» leads: a joke page in the genre of stupid.fish technologies (a grid of homelab memes, just the
  pictures: drop one into `content/memes/` and push; site-api lists them, crops them square and pages them) and a live
  fastfetch of the Proxmox host at `/fetch` (not linked from the page); its 88x31 is `/88x31/infra.gif`
- `assets/css/`: plain CSS split by component; `site.css` lists them as `@import`s and site-api joins
  them into one file
- `assets/js/`: `rack.js` (shared by the rest: what the units declare about themselves, cable physics, the hand that
  takes a plug, the cable tester, the toys' memory and the visitor's settings in localStorage, reduced motion, the
  animation the aisle and the avatars glide by, the list of `rack:*` events; `theme.js` reads the theme itself, before
  the first paint),
  `app.js` (Alpine components, unit heights, rail numbers, the network cables), `power.js` and `net.js` (power plugs
  and network cords to pull), `aisle.js` (walking along the row), `live.js` (guests online, packets), the toys
- `assets/vendor/`: htmx 2.0.4 and the CSP build of Alpine.js 3.17.4, self-hosted
- `assets/fonts/`: Tektur, Handjet, IBM Plex Sans and Caveat, self-hosted (SIL OFL)
- `assets/og/`: link preview images (Open Graph): one for the whole site, one for the infrastructure page, drawn by
  `node docs/tools/og/make.mjs`
- `robots.txt`: static; `/sitemap.xml` is generated by site-api from `content/racks.yaml`
- `index.html`: a static fallback page for when site-api is down
- `docs/`: the tools (88x31 buttons, the preview image, screenshots, the theme check) and the record of the
  2026-10-12 code audit, not deployed

## Run locally

```sh
git clone https://git.belomaxorka.dev/belomaxorka/site-api ../site-api
cd ../site-api && go run ./cmd/site-api -site ../belomaxorka.dev -addr 127.0.0.1:8090
```

Open http://127.0.0.1:8090, edit a template or a stylesheet and reload: site-api picks up changes
within two seconds.

## Changing things without Go

Push, and site-api picks the change up by itself:

- monitoring lamps: a new endpoint in the Website, Services or Infrastructure group of the infra repository's
  `gatus/config.yaml` appears on the monitor; its short caption goes into `content/lamps.yaml`
- racks: `content/racks.yaml` (which racks, at which addresses, which units in which order); a new rack also needs
  `rack.<id>` and `rack.<id>.sub` in both i18n files. A unit without a template in `templates/units/` fails the check
  in CI, and on the server the previous version keeps running
- the profile, contacts, buttons, donations: `content/*.yaml`; every text: `i18n/en.json` and `i18n/ru.json` (CI fails
  on a key a page asks for that a dictionary lacks, or that only English has); an address the templates link to:
  `content/links.yaml`
- the meme wall of the infrastructure page: a picture dropped into `content/memes/`

## Real and simulated

- The data is real: site-api reads the live sources (Koito, Gatus, Proxmox, NUT, Telegram, Wakapi, the webring) and
  the page refreshes units as soon as their source has something new.
- The bright packets and the blinks along their way are real events: each stands for something site-api did (a
  request served, a source fetched, a file written, a Gatus check that ran), sent once a second over the live stream.
  Where they run is the rack's topology: a source from outside the home network (site-api tells which, from its
  address) comes in through the WAN, one from inside comes from the server, to the units that show it (`data-feed`).
  Besides them the page plays the background chatter every network has (`live.js`): dim packets to any unit, ports
  and network cards flickering, the server's disk at work; it stands for nothing and refreshes nothing, by the same
  rules of power, links and the internet.
- The toys (plugs, cords, the UPS, the breaker) are simulated for each visitor and change nothing on the server; the
  page then behaves as the rack would, by one rule (`Rack.live`, `Rack.reached` in `assets/js/rack.js`): a unit
  without power or a link gets nothing (no data, no blinks, its screen stands still and says why), a rack without the
  internet gets nothing from outside (no visits, no other visitors' cords and torches); back online, a unit catches up.
  The visitor is not simulated: the page itself stays reachable whatever is pulled.

## Adding a unit

A unit is a template in `templates/units/` whose root element says what it is; the scripts go by that, not by names
(the reference is at the top of `assets/js/rack.js`):

- `data-key="name"`, and `data-power` if it has its own power supply: it gets a power cable from the PDU and goes dark
  when its plug is pulled, the UPS is off or its battery empty;
- `data-net="lan"` or `"wan"` if it is on the network: it gets a network card and a cord to the switch, and is offline
  without a link (lan) or also without the internet (wan); its screens say which;
- `data-host="key"` instead, if it runs on another unit (like a container on the host): no cables of its own, it is on
  and online while its host is;
- `data-live="lamps|bar|text|image"` on what shows live data: it goes dark while the unit is offline;
- `data-feed="source ..."` for the server's sources it shows (packets go there: koito, gatus, proxmox, ups, wakapi,
  webring, telegram, and the server's own site and guestbook; CI refuses another name), `data-news` on what changes
  with new data.

Then a line in `content/racks.yaml` and a `lite-<name>` template for the light version. CI
(`docs/tools/check-units.mjs`) refuses a unit that shows live data without saying how it gets it.

## Deploy

Push to `main` → CI (`.forgejo/workflows/deploy.yml`): first `site-api -check` with site-api's `main` renders every
page of the commit (each rack in each language, pulled-out units, the light and infrastructure pages, the htmx
fragments), and `docs/tools/check-themes.mjs` checks that the theme is switched in one place (tokens.css); only then the site is
shipped to the server, where site-api picks the new release up by itself.
